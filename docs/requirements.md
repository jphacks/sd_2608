# 機能要件・仕様書

作成日：2026-10-17。今回の対象は **長時間座り続けている可能性を伝える休憩通知** と **作業レポート** の2機能。以下の秒数・上限は初期値とし、実機確認後に定数で調整する。

## 1. 範囲と用語

| 用語 | 定義 |
|---|---|
| 在席 | 顔有無と PC 情報から推定する状態。実際の着座・起立や健康状態を断定しない |
| 連続在席 | 安定した在席から、確定離席または観測不能による中断までの連続区間 |
| 区切り | 入力停止・前面アプリ切替から推定した、通知を出しやすい瞬間 |
| 作業セッション | 連続在席を識別する ID。確定離席・中断後の安定した在席で新しく採番 |
| レポート | 直近の作業履歴をまとめたカード。AI 設定時は概要・根拠となる履歴・次の作業候補を表示 |

悪姿勢判定、画面の見すぎの判定、毎日の記録・日次集計、撮影・OCR、他 OS 対応は今回実装しない。各々を独立モジュールとして追加できる境界を設ける。

カメラ内で立ったまま顔が映っている場合、顔有無だけでは起立を確認できない。この段階での「ずっと座っている」は在席の推定として扱い、姿勢推定と混同しない。

## 2. 取得と在席・離席の推定（FR-01）

顔と PC 情報を約1秒ごとに取得する。顔の5回の異なる有効サンプル中3回以上が顔あり、かつ最新も顔ありなら安定した在席とする。同じサンプルの再送は票に加えない。

以下の30秒は通常プロファイルの値。短縮デモでは顔なし・入力停止・連続性中断のしきい値を5秒にする。サンプル鮮度の5秒と、顔の5回中3回の安定化は変更しない。

| 状態 | 条件と動作 |
|---|---|
| `present` | 顔が安定して見え、PC 情報が有効。入力が止まっていても在席を維持 |
| `uncertain` | 顔が安定化中、または顔なしが継続30秒未満。通知を隠す |
| `away` | 顔なし30秒以上 **かつ** 入力停止30秒以上。離席を1回だけ確定 |
| `unknown` | 顔・PC 情報が5秒超更新されない、停止・エラー、ロック等の保護画面。通知・計測を止める |

- 顔なし30秒未満の短い欠落は連続区間を維持し、短い欠落時間も在席時間に含める。離席確定時は区間の終了を顔なし開始時刻とする。
- 顔なしでも入力が続いている場合は `uncertain` とし、離席と断定しない。30秒に達したら在席の連続性を中断し、次の安定した顔ありから再計測する。この中断ではレポートを予約しない。
- `away` から安定した顔ありへ戻ると新セッションを開始する。入力だけで着席復帰とは判定しない。
- `unknown` へ変化した場合は連続性を中断する。センサー復帰で古い時間を持ち越さない。単なる顔の欠落と、サンプル自体の停止を区別する。
- 本番は顔と PC の両方を使用する。カメラが使えない場合は説明を出して計測を停止し、デモ専用の手動入力を別モードで用意する。

## 3. 区切りと休憩通知（FR-02）

### 通知の初期値

| 項目 | 通常 | 短縮デモ |
|---|---|---|
| 最初の休憩目安の予告 | 在席27分（30分の3分前） | 在席27秒（30秒の3秒前） |
| 最初の提案が可能になる連続在席時間 | 30分 | 30秒 |
| 最初の提案で区切りを待つ上限 | 5分（35分で提案） | 5秒 |
| No 後の最大延期 | 10分 | 10秒 |
| No 直後の区切り再通知の抑制 | 2分 | 2秒 |
| 区切りを待たなくなる連続在席時間 | 60分 | 60秒 |
| 60分以降に No で閉じた後の再通知間隔 | 5分 | 5秒 |
| Yes 後、離席しなかった場合の再提案猶予 | 10分 | 10秒 |
| 自然離席からレポート実行まで | 5分 | 5秒 |

区切りは **入力停止が5秒に到達**、または **外部ウィンドウ切替後10秒以内に入力停止が2秒に到達**したときに1つ発行する。短縮デモでは順に2秒・5秒・1秒。ウィンドウはプロセス ID とウィンドウ ID で識別し、タイトル変更だけでは切替扱いにしない。ペット自身・除外対象・保護画面は区切り対象から外す。

### 通知ルール

最初の30分の目安の3分前から、在席中に限り「あと3分ほどで休憩の目安だよ」のような控えめな予告を表示する。短縮デモは27秒から3秒前の予告とする。残り時間は Rust の単調時計から算出し、分／秒単位で切り上げて表示する。予告には「閉じる」だけを置き、Escape でも閉じられる。閉じても No として回答せず、提案の延期・在席時間のリセット・レポート生成を行わない。同じ監視・在席セッション内では再表示せず、新しい在席セッションまたは監視の再開始で予告対象を更新する。閉じた状態はアプリ内の表示状態として保持し、アプリの再起動をまたぐ保存はしない。

30分（デモ30秒）になったら予告を消し、以下の従来の休憩提案ルールへ進む。予告によって30分での休憩や提案表示を確約しない。在席が不確実・離席・観測不能・監視停止中は予告も表示しない。設定・メニュー・履歴・レポート・生成中の表示を優先し、予告で操作を遮らない。予告のために音や強いアニメーションを追加しない。

1. `present` かつ連続在席30分以降、新しい区切りがあれば「しばらく座りっぱなしかも。少し立って休憩しない？」を **Yes／No** 付きで表示する。区切りがなければ35分で表示する。
2. No はレポートを作らず、約10分延期する。ただし回答後2分を過ぎてから発生した **新しい区切り** があれば、その時点で再通知する。10分経過時は区切りを待たない。同じ入力停止を繰り返し使わない。
3. No が続いても、連続在席60分に達した時点で延期を打ち切り、区切りを待たずに再通知する。60分の起点は連続在席開始であり、最初の No ではない。
4. 60分以降も No は選べる。閉じた後は5分間隔で再通知し、次のティックで即座に開き直さない。この5分は連打防止用の初期値。
5. Yes はレポートを即時作成し、通知を閉じる。ただしクリックだけで実際の起立を確認したことにはせず、連続在席時間はリセットしない。離席しない場合は10分後に再提案する。60分を未通過なら、その到達時の再通知を優先する。
6. `uncertain / away / unknown` の間は、60分を超えても休憩提案を表示しない。自分で席を離れたユーザーを呼び戻す通知は出さない。
7. 表示中の提案を毎秒作り直さない。回答・離席・停止で失効するまで同じ通知 ID を使う。Escape は No と同じ扱い。

60分到達時に通常提案を表示済みなら、通知 ID を維持して強い表現へ更新する。No の再通知時刻や Yes の猶予中なら60分到達で再表示する。60分以降に回答した No／Yes の猶予は、それぞれ5分／10分を守る。

**強制するのは再通知の表示だけであり、休憩や AI 送信・レポート生成を強制しない。** 文言は作業量を責めず、立って体を動かすきっかけを伝える。画面の見すぎ・姿勢に関する警告はここへ混在させない。

例：30分で提案 → No → 32分以降の区切り、または40分で再提案 → No が続く → 60分で区切りに関係なく再提案。途中で確定離席すれば通知と連続在席時間をリセットする。

## 4. レポート（FR-03）

| 契機 | 動作 |
|---|---|
| 休憩提案の Yes | 回答受付時に履歴を固定し、即時に生成開始 |
| 自然離席の確定 | 離席開始までの履歴を確定時に固定し、**確定時刻から5分後**に生成開始 |
| No | ジョブを作らない。次の通知で Yes、または自然離席が発生するまで先送り |
| 帰席 | 既存予約を維持。生成時刻を変更しない |
| 生成完了 | 完成したカードを即表示。ユーザーが戻ったかを条件にしない |

- 1作業セッションにつきレポートジョブは1つ。Yes 後の離席や二重クリックで追加しない。Yes 後も座り続けて再度 Yes を選んだ場合は既存ジョブ・レポートを再表示する。
- 新しい在席セッションでは別のレポートを作れる。旧セッションの予約も残せるため、セッション ID で管理する。
- 対象は **そのセッション内の直近30分・最大600区間** の履歴。予約から実行までの新しい作業を混ぜない。30分を超えた連続在席でも全文の履歴を保持する必要はない。
- 取得するのはアプリ名・ウィンドウタイトル・区間時刻。キー入力内容・画面画像・顔画像は取得・保存・送信しない。連続する同一ウィンドウ・同一タイトルは区間にまとめる。
- 保存前に URL・メール・ユーザーパス・認証情報らしい文字列をマスクし、除外アプリ・ペット自身・保護画面を記録しない。AI へはマスク済み履歴の文字情報だけを送る。
- レポートは概要、根拠となる履歴、次に取り組むことの候補、作成契機・対象時間を表示する。AI の推測と観測履歴を区別し、ユーザーが閉じた後もペットから再表示できる。
- AI は設定で選択する。初回の監視開始時に送信先・対象データ・Yes 時の即時送信と離席5分後の送信を説明して同意を得る。**今回の Yes は、送信前プレビューを開く旧プロトタイプの動作から、即時レポート作成へ変更する。**
- 同意しない場合・API 未設定の場合はローカル履歴カードを生成する。AI 通信は60秒でタイムアウトし、自動再試行しない。失敗時も履歴とエラーをカードに残し、明示的な再試行を用意する。履歴が空なら外部送信せず、記録がないカードを作る。
- 外部通信は同時に1件まで。予約は予定時刻・作成順に処理し、手動の即時生成は未開始の予約より優先する。実行中ジョブは割り込まない。

## 5. ペットと UI（FR-04）

表示はペット、吹き出し、Yes／No 付きメッセージ、レポートカードを中心にする。開始・停止、AI 設定、取得状態の確認はペットのメニューから開く。

| 素材 ID / GIF ファイル案 | 用途 | 再生と終了後 |
|---|---|---|
| `launch` / `launch.gif` | 1. アプリ起動 | 1回 → `runIn` |
| `runIn` / `run-in.gif` | 2. 犬が走り込む | 1回 → `welcome` |
| `welcome` / `welcome.gif` | 3. 「おかえりなさい！」 | 1回 → お座り静止。確定離席からの帰席時にも使用 |
| `idleRest` / `idle-rest.gif` | 4. 休憩中・待機中 | 伏せ姿勢でループ |
| `recordReminder` / `record-reminder.gif` | 5. 作業記録・休憩リマインダー | 通知・レポートの表示時に使用。終了後はお座り静止 |
| `sitToLie` / `sit-to-lie.gif` | 6. お座りから伏せ | 1回 → `idleRest` |
| `lieToSit` / `lie-to-sit.gif` | 7. 伏せからお座り | 1回 → 通知用 GIF またはお座り静止 |

- 通常の作業中はお座り静止、待機・確定離席中は伏せ。起動演出の終了時に現在の業務状態へ合わせる。通常の表現切替は `sitToLie / lieToSit` を経由する。
- アニメーションは業務の状態と別に管理する。GIF の終了でレポートを生成したり、在席時間を変更したりしない。
- GIF 自体に再生終了イベントはないため、manifest に `durationMs / loop / finalPose / poster` を記載する。1回再生は新しい画像インスタンスで再開し、時間経過後に静止画像へ切り替える。古いタイマーは再生トークンで無効化する。
- 通知と完成カードは GIF の終了を待たずに表示する。伏せからの復帰演出は並行して行う。素材欠損・動きを減らす設定では静止画像へ切り替え、操作は維持する。
- 完成レポートは自動で前に出す。複数同時に完成したら完成順に表示キューへ入れ、現在のカードを勝手に上書きしない。休憩提案はカード脇の吹き出しに併記し、双方を操作可能にする。
- 取得エラーや監視停止の案内は常に確認できる表示とし、あいさつ・演出より優先する。あいさつが操作を妨げないようにする。

## 6. 初期状態・保存・受入条件

監視・カメラ・PC 取得・履歴記録・外部送信は起動時オフ。開始には説明と操作が必要。再起動時に自動再開せず、設定と完成済みレポートだけを復元する。レポートは最新20件かつ7日以内を保持し、設定画面から全履歴・レポートを削除できる。API キー削除は別操作とする。

| ID | 確認すること |
|---|---|
| AC-01 | 顔あり・入力停止でも在席を継続し、顔なし＋入力停止30秒で通知が消える |
| AC-02 | 30分以降の区切り、区切りなし35分、No 後2〜10分の再通知が指定どおり動く |
| AC-03 | No を繰り返しても60分で通知し、その後の No は5分の間隔を空ける。No だけでレポートを作らない |
| AC-04 | Yes で即時生成、自然離席確定から5分後に生成。帰席しても予約は残り、完成後すぐ表示される |
| AC-05 | Yes と離席の競合、二重クリック、イベント再送でも1セッション1ジョブ。失敗の再試行も同じ ID を使う |
| AC-06 | 顔・PC 情報の停止、ロック、スリープで誤通知しない。停止後に古いサンプルや完了結果が状態を復活させない |
| AC-07 | 7つの GIF、静止画への代替、割り込み、Escape、カード再表示、表示倍率100%／125%／150%を確認する |
| AC-08 | API 失敗・履歴なしでもカード表示を続けられ、AI 未同意時は外部通信が発生しない |
| AC-09 | 27分／デモ27秒で予告し、閉じる・Escape は表示だけを閉じる。同じサイクルで再表示せず、30分／30秒以降の Yes／No の提案とレポート生成を変えない |

時間に依存する条件は注入時計の単体テストと短縮デモの両方で確認する。実カメラ・Windows 取得・実 API の確認結果はモック検証と分けて記録する。
