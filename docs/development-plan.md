# 休憩支援デスクトップペット 開発計画

2人で「ペットの表示」と「ロジック」を並行開発し、作業から休憩・振り返りまでを実演できるアプリを完成させる。各フェーズの実装手順・詳細仕様は、着手時に別の計画書へまとめる。

表示作業を先行するため、共通型・モック・接続用コントローラー・UI ひな型を先に整備した。[表示開発ガイド](ui-development.md) に従い、表示担当は phase3 まで連続して作業できる。実ロジックの各フェーズの完了とは区別する。

## 1. 開発の前提と完成目標

- 開発・提出先は **`sd_2608`**。Tauri 2 + React + TypeScript に表示開発用の共通基盤を追加。実センサーと本番ロジックは未接続。
- **`break-support-pet`** は参考・移植元とする。顔検出、PC 情報取得、休憩判定、履歴保存、AI 要約、自動要約の既存実装を必要な単位で取り込む。
- 最初の対象は、プロトタイプの OS 固有処理を利用できる **Windows** とする。
- 基本デモは **「ペット表示 → 顔・PC 情報による連続在席の計測 → 約30分の休憩提案 → Yes でレポート作成 → 即表示・再表示」**。No 後は約10分、または新しい区切りで再通知し、連続在席60分では区切りを待たず再通知する。
- **自然離席確定から5分後のレポート作成も必須範囲**。帰席で取り消さず、完成後すぐ表示する。悪姿勢判定・画面の見すぎ・毎日の記録は将来の独立機能とし、撮影・OCR は今回の対象外とする。

## 2. 担当と変更範囲

以下の配置は、本開発で整備する構成案。

| 担当 | 責任範囲 | 主に変更する場所 |
|---|---|---|
| A：表示担当 | 7種の GIF・アニメーション制御、吹き出し、設定画面、レポートカード、操作しやすさ | `src/components/`、`src/styles/`、`src/presentation/`、`public/pet/` |
| B：ロジック担当 | 顔検出・PC 情報取得、在席／離席・休憩判定、レポート予約、履歴保存、AI 接続、停止・エラー処理、画面への接続 | `src/application/`、`src/adapters/`、`src/ports/`、`src-tauri/src/`、`src/App.tsx` |
| 共同 | 共通の型、機能の優先順位、統合確認、デモ・発表 | `src/contracts/`、`docs/`、README |

React の Hook や状態の接続も B が担当し、A は渡された状態を描画して操作を通知する。判定・予約の正規状態は Rust に集め、顔検出と表示は TypeScript で実装する。B は統合担当を兼ねる。ウィンドウの透過・最前面・移動などは A が要件をまとめ、B が Tauri 側へ反映する。

`App.tsx`・依存定義・lock ファイル・Tauri 設定は B を編集窓口とし、A の変更が必要な場合は事前に共有する。CSS は担当コンポーネントごとに分け、共通スタイルの同時編集を避ける。

## 3. 表示とロジックの接続方針

データの流れは **取得・判定 → 表示用の状態 → UI → ユーザー操作 → ロジック** に統一する。

| 接続するもの | フェーズ0で合意する内容 |
|---|---|
| ペット・通知の状態 | 登場・あいさつ、待機、作業中、休憩提案、休憩中と、それぞれの表示 |
| 履歴・要約の状態 | 未取得、予約中、処理中、完了、失敗と、表示するデータ |
| ユーザー操作 | 開始、Yes、No、設定変更、カード再表示、再試行、停止 |
| 共通の型とモック | Props・コールバック・エラーの形式と、各状態を再現する固定データ |

- A は共通の型に従うモックで開発し、カメラ・API・Rust の完成を待たずに画面を確認できるようにする。
- B は同じ型の実データと操作関数を提供する。UI コンポーネントから取得処理・タイマー・AI 通信を直接実行しない。
- パネルの開閉など表示だけの状態は A、休憩・保存・送信に関わる状態と実行可否は B が管理する。型の変更は2人で合意し、モックも同時に更新する。

## 4. 開発フェーズ

| フェーズ | A：表示担当 | B：ロジック担当 | 完了条件 |
|---|---|---|---|
| **0：仕様・接続の合意** | ペットの表現と画面遷移を整理 | 移植する機能と状態・操作を整理 | 必須機能、共通の型、担当範囲、デモ手順を合意し、2人の環境で起動できる |
| **1：並行開発の土台** | 表示コンポーネントと状態切替モックを用意 | 移植用の構成、依存・モデル等の準備、画面への接続口を用意 | 実センサー・通信なしで、基本デモの全画面と操作を確認できる |
| **2：通知・即時レポートの統合** | ペット、通知、設定、レポートカードを仕上げる | 取得・休憩判定・Yes／No・履歴・即時レポートを接続 | 短縮時間で基本デモが通り、No 後の区切り・延期・60分相当の再通知が動く |
| **3：離席予約・体験の完成** | 帰席演出、完成カードの即表示、GIF の割り込みを仕上げる | 自然離席5分後のレポート予約、重複防止、帰席後も継続する生成を実装 | Yes と自然離席の両経路、旧セッションの完成表示、失敗時のカードまで通し確認できる |
| **4：安定化・発表準備** | 見切れ・操作性を確認し、発表用の画面と素材を整理 | 例外処理・ビルド・デモ設定を確認 | デモ機の単体アプリで実演でき、予備の録画・手順・README がそろう |

フェーズ1以降は2人で並行作業し、**各フェーズの終了時に必ず統合する**。フェーズ2では「休憩提案まで」「履歴・要約まで」の途中でも接続を確認する。全体の最後の約20%はフェーズ4に確保し、新機能の追加を止める。

## 5. 共同開発と確認のルール

- Issue に担当・対象ファイル・完了条件を記載し、機能単位のブランチと小さな PR で進める。相手の確認後に統合する。
- プロトタイプの参照コミットと移植範囲を記録する。機能本体に加え、関連テスト・依存・モデル資産・Tauri 権限を一緒に確認する。
- B は移植した判定・保存・通信の関連テストを整備し、統合時にテストと `npm run build` を実行する。`npm test` はモックと表示用コントローラーの検証を実装済み。
- 2人で Windows 実機の通し操作を確認する。表示倍率、カメラ拒否・停止、API 失敗、離席・復帰を含め、必要に応じてロック・スリープも確認する。
- 取得・保存・外部送信は初期オフとする。開始時に Yes と自然離席5分後の送信を説明して同意を得る。未同意・API 未設定ならローカル履歴カードを使う。API キーと実作業の履歴はリポジトリへ入れない。
- カメラや通信が使えない場合に備え、手動入力・固定応答・履歴のみのカードで操作を確認できるようにする。デモでは実データとモックの使用箇所を明示する。

## 6. 各フェーズの詳細計画に書くこと

詳細計画は `docs/phase-0-plan.md` 〜 `docs/phase-4-plan.md` に順次作成する。各文書では **目的・対象／対象外、担当と変更ファイル、接続仕様、実装順序と依存関係、確認方法と完了条件** を具体化する。日時と作業量は残り時間を見てフェーズ0で割り当て、後続フェーズの範囲は統合結果に応じて調整する。

参考：プロトタイプの [設計・実装計画](../../break-support-pet/docs/break_pet_prototype_plan.md)／[チーム開発準備](../../break-support-pet/docs/team-development.md)。
